# Устройство изнутри

Три слоя, между которыми проходят ясные границы: **коннекторы** достают
данные, **слоты** их хранят, **раскладка** рисует. Каждый слой можно менять,
не трогая соседние, — и это не абстракция ради абстракции, а прямое следствие
того, как проект ломался у предшественника: там разбор ответа API и вёрстка
блока знали друг о друге, и правка в одном месте молча гасила блок в другом.

## Слот

Именованная ячейка. Всё, что попадает на экран, сначала становится слотом.

```cpp
struct Slot {
    String id;          // "btc", "usd_rub", "co2", "limit.claude"
    String text;        // готовое к печати значение
    float number;       // оно же числом, когда нужно рисовать шкалу
    float delta;        // изменение, если источник его даёт
    uint32_t at;        // когда получено, unix-время
    uint32_t ttl;       // сколько считается свежим, секунды
    bool ok;            // источник ответил без ошибки
};
```

Два правила, оба выстраданы:

**Возраст хранится рядом со значением.** Не в глобальной «дате обновления», а
у каждого слота свой. Курс может прийти минуту назад, а почта — час; экран
обязан показывать это раздельно, иначе он врёт целиком из-за одного
отвалившегося источника.

**Пустой слот и нулевой слот — разные вещи.** `ok == false` рисуется
прочерком. Ноль процентов, показанный вместо «нет данных», читается как
«свободно» — на лимитах это уже вводило в заблуждение.

## Коннектор

Источник данных. Знает, куда сходить и как разложить ответ по слотам. Ничего
не знает про экран.

```jsonc
{
  "id": "home",
  "kind": "homeassistant",          // homeassistant | http | none
  "url": "http://192.168.1.2:8123",
  "token": "…",                     // хранится в NVS, наружу не отдаётся
  "interval": 300,                  // как часто спрашивать, секунды
  "map": [
    { "slot": "co2",  "entity": "sensor.abinetco2",       "ttl": 300 },
    { "slot": "tvoc", "entity": "sensor.abinetairquality", "ttl": 300 }
  ]
}
```

Для `kind: "http"` вместо `entity` — путь в JSON-ответе:

```jsonc
{
  "id": "rates",
  "kind": "http",
  "url": "https://api.example.com/rates",
  "interval": 300,
  "map": [
    { "slot": "btc",     "path": "bitcoin.usd",     "ttl": 300 },
    { "slot": "usd_rub", "path": "usd.rub",         "ttl": 900 }
  ]
}
```

Коннекторы независимы: один отвалился — его слоты протухают, остальные живут.
Никакой общей точки отказа.

**Чего коннектор не делает.** Не ходит в OAuth, не разбирает почту, не хранит
долгоживущих секретов сверх одного токена доступа. Всё это живёт на большой
машине и приезжает сюда готовыми значениями — [почему](decisions.md#2).

## Раскладка

Берёт слоты и рисует кадр. Единственный слой, знающий про пиксели — но не про
то, кто именно кладёт их на физический экран (см. «Канва» ниже).

Реализована в `firmware/src/layout.{h,cpp}` (фаза 3) как **точное
воспроизведение сетки предшественника** — `trmnl-ink/renderer/app/templates/
cockpit.html`, обмеренное по живому кадру `reference/cockpit-reference.png`
(`tools/compare_frame.py`, см. ниже). Первая версия фазы 3 сделала три равных
блока в ряд («Рынки/Лимиты/Воздух по трети экрана») — это оказалось
самостоятельной, не утверждённой владельцем адаптацией дизайна, а не его
воспроизведением; текущая версия — ровно то, что рисует cockpit.html:

- верхний ряд — ДВЕ колонки: Рынки фиксированной ширины (296px, `flex:none`
  в CSS-оригинале) слева, и одна гибкая колонка справа, где друг под другом
  стоят Лимиты и Воздух — та же рубрика (`draw_eyebrow`), что осталась бы
  первой в потоке, если бы верхняя отсутствовала (`draw_limits_and_air`
  ведёт себя как последовательный поток документа: у скрытого раздела нет
  ни своей строки, ни отступа под неё, — совсем как `{% if %}` в Jinja);
- нижний ряд — тоже две колонки, но зеркально: Сегодня фиксированной ширины
  (202px) справа, Почта — гибкая слева;
- видимость всей колонки — по `rates_visible`/`limits_visible`/`air_visible`/
  `mail_visible`/`today_visible` (истина, если хоть один из её слотов не
  пуст); `compute_columns_fixed_first`/`compute_columns_fixed_second`
  реализуют фиксированная+гибкая колонка с тем же правилом «пропала —
  сосед получает всю ширину ряда»;
- `compute_two_rows()` — то же по вертикали, пропорция верх/низ (~60/40) —
  тоже обмер эталона, не круглое число.

### Сверка с эталоном — `tools/compare_frame.py`

Раз кадр не рисуется по формуле «в точности эти пиксели» (данные другие,
координаты — итог обмера одного снимка), проверка на глаз ненадёжна: три
блока вместо двух в первой версии тоже "выглядели похоже". Скрипт находит в
обоих PNG (проверяемом и эталонном) горизонтальные/вертикальные линии-
разделители — самый длинный сплошной пробег тёмных пикселей в строке/столбце,
текст такого пробега не даёт — и построчно сверяет их координаты и охват.
Гонять после любой правки геометрии:

```bash
python3 tools/compare_frame.py tools/render_frame/out/full.png reference/cockpit-reference.png
```

«ВСЁ СОШЛОСЬ» — все линии эталона нашлись в кадре в пределах 4px. Числа
совпадений/расхождений — не for-the-record: именно ими фаза калибровалась
(Status Log, .claude/plans/inkroam.md).

Пустых рамок с надписью «нет данных» на экране не бывает: место отдаётся
соседям. Значение внутри видимого блока, если оно всё же не пришло, — прочерк
(`format_percent`/`format_value`), не ноль.

Это ровно то поведение, что утверждено у предшественника, — см.
`trmnl-ink/docs/frame-contract.md`. Оттуда же переехали кегли (шрифт —
`firmware/assets/`, README там же объясняет конвертацию из BDF и решение по
UTF-8) и правила свежести. Состав блоков и доступные им поля слотов —
комментарий в начале `layout.h`.

В самой раскладке используются только 14/16/20/24 — минимум из правила
«кегли только из сетки Terminus, минимум 14px» (docs/decisions.md, п.6) не
пускает в кадр сгенерированный заодно 12 (при 12px разница высоты прописной и
строчной кириллической буквы — пара пикселей, на глаз воспринимается как один
регистр; см. Status Log). Курс BTC поднят до зрительно доминирующего размера
без пятого файла шрифта: `fonts::draw_text()` умеет целочисленный множитель
(`scale`), 24×2 даёт те же физические пиксели на штрих, что дал бы
гипотетический кегль 48 из той же сетки, — растровому шрифту можно доверить
только кратное увеличение, не дробное.

### Канва

Раскладка рисует через `canvas::Canvas` (`firmware/src/canvas.h`) — интерфейс
из пикселя, линии и прямоугольника, ничего не знающий о том, кто в итоге
проявляет кадр. Две реализации:

- `canvas::CanvasGxEPD2` (`canvas_gxepd2.h`) — на устройстве, тонкая обёртка
  над `GxEPD2_BW`;
- `canvas::CanvasMemory` (`canvas_mem.h/.cpp`) — на хосте, копит кадр в ОЗУ и
  умеет сохранить PNG без внешних библиотек (zlib-поток с несжатыми блоками
  deflate, ручной CRC32/Adler32).

Без этого разделения раскладку можно было бы проверить только на живой
панели — а она либо занята другим проектом, либо физически недоступна
(`docs/decisions.md`, п.6). `tools/render_frame/` — маленькая хостовая
программа поверх `CanvasMemory`: рисует кадр по трём сценариям (полный набор
источников / часть отвалилась / ни одного не настроено) в PNG, чтобы
типографику и пересборку сетки можно было посмотреть глазами без прошивки.

## Где что хранится

| Что | Где | Почему |
|---|---|---|
| Сети Wi-Fi, токены | NVS | переживает перепрошивку, не лежит в файловой системе открытым текстом |
| Описания коннекторов | NVS, одним JSON | меняется целиком, читается при старте |
| Страница настройки | LittleFS | обычные файлы, заливаются отдельно от прошивки |
| Слоты | ОЗУ | смысла переживать перезагрузку нет: источники опрашиваются заново |
| Последний кадр | ОЗУ | после перезапуска рисуется заново — иначе свежая правка ждала бы на экране |

## Цикл

```
старт
  └─ поднять панель, показать, что живы
  └─ подключиться к сохранённым сетям
       ├─ удалось  → рабочий режим
       └─ не удалось → точка доступа + страница настройки
рабочий режим, по кругу:
  └─ у кого истёк interval — опросить
  └─ изменились слоты → перерисовать изменившиеся блоки (частичное обновление)
  └─ раз в сутки и после длинной череды частичных → полное обновление
```

Частичное обновление — по умолчанию: полное моргает всем экраном около
секунды. Но копить частичные бесконечно нельзя — остаётся остаточное
изображение, поэтому полное вызывается по расписанию и по счётчику.
